# Учёт рабочего времени — product intent

**Issue:** [#1](https://github.com/AlexKovalko/falconai/issues/1)  
**Slug:** `time-tracking`  
**Источник:** `docs/TZ.md`, стек зафиксирован в `docs/STACK.md`  
**Статус решений:** grill отвечен — решения ниже **locked**

## Intent

Небольшое greenfield веб-приложение для учёта рабочего времени сотрудников компании (тестовое / portfolio задание). Пользователь без авторизации и ролей работает с **вымышленными** данными (допустим seed через **faker**): полный CRUD сотрудников и записей времени, запуск/остановка таймера с описанием задачи, live-elapsed с возможностью скрыть/вернуть таймер, отчёт за период с CSV-экспортом, тёмная тема и UI на **ru + en**. Данные переживают перезапуск (SQLite + volume в Docker Compose).

**Качество:** чуть выше baseline portfolio — аккуратная сборка и проверяемые сценарии **без** сложности ради сложности (нет queues, auth, billing и т.п.).

Интерфейс — простой single-page (3 блока); приоритет — работающий результат, понятные сценарии и проверяемое поведение (повторный Start при running, empty report, hide/restore таймера, CRUD, экспорт).

### Цель оценки (наравне с работающим результатом)

Задание оценивает не только «оно запускается», но и **осмысленное применение ИИ** (в **процессе разработки** + раздел README) и **аккуратную сборку** — не «сгенерировать кучу кода и забыть». **ИИ не является in-app фичей** продукта.

1. **Meaningful AI use** — в README видно, какими моделями/инструментами пользовались; есть примеры промптов; явно сказано, где ИИ помог, где ошибся, и что поправили вручную.
2. **Craft** — код и слои читаемые; архитектура согласована с `docs/STACK.md` и `docs/TZ.md` (отдельные приложения **API** NestJS и **UI** React + TanStack Query + Tailwind + shadcn/ui, SQLite, Docker Compose / nginx).
3. **Demonstrable workflow** — решение можно объяснить и доработать; ИИ — помощник в цикле, не замена ревью.

Функциональные AC не ослабляются: craft/AI — дополнительные done-критерии рядом с рабочим продуктом.

## Рынок / альтернативы → выбор

### Кого смотрели (паттерны)

| Продукт / класс | Что делают | Что избыточно для ТЗ |
| --- | --- | --- |
| [Toggl Track](https://docs.toggl.com/overview-of-the-timer-page) | Timer bar: описание → Start/Stop; live elapsed; история; период в отчётах; экспорт | Проекты, теги, calendar/timesheet, Pomodoro, billing |
| [Clockify](https://clockify.me/help/getting-started/track-your-time-as-regular-user) | Выбор контекста → Start/Stop; Summary/Detailed + date range; export | Проекты, billable, роли |
| iXTime / аналоги reports | Период (week/month/custom) + список + totals | Много вкладок отчётов, utilization, changelog |

Общий паттерн рынка: **один активный таймер на пользователя/сотрудника**, явный Start/Stop, описание при трекинге, отчёт с **диапазоном дат**, суммы, часто **экспорт**.

### Подходы (2–4)

| # | Подход | Плюсы | Минусы | Риск / сложность |
| --- | --- | --- | --- | --- |
| A | **Одна страница, 3 блока:** сотрудники · таймер · отчёт за период | Минимум навигации; покрывает ТЗ; удобно для демо | Плотно на узком экране | Низкая — **рекомендуется** |
| B | Wizard / отдельные экраны на каждый шаг | Чище по фокусу | Лишние клики; больше UI без выигрыша | Средняя — отклонено |
| C | Timesheet-сетка (часы вручную по дням) | Быстрый bulk-ввод | Не отражает timer start/stop из ТЗ | Высокий miss — отклонено |
| D | Несколько параллельных таймеров без guard | Гибко | Сложно тестировать; расходится с рынком | Высокий — отклонено |

### Рекомендация (default) — locked после grill

**Подход A + правила:**

1. **Одна основная страница** (лёгкие секции/якоря допустимы).
2. Выбрать сотрудника → описание задачи → **Start** → live elapsed → **Stop** закрывает запись.
3. **Не более одного running-таймера на сотрудника** (даже если UI не multi-user concurrent — правило **per-employee**). Повторный Start при running у этого сотрудника — **отклонить** с сообщением (без авто-стопа). **Locked.**
4. **Live timer в UI:** показывать elapsed; можно **скрыть**; при **первом** hide — спросить один раз: **завершить сессию** или **скрыть таймер**; после скрытия — **восстановить** и **остановить, пока свёрнут**.
5. **Полный CRUD** сотрудников и time entries — **обязателен**.
6. **Отчёт:** период с/по, список + итоги по сотрудникам; empty state; **CSV export** данных отчёта.
7. **Тема (light/dark)** и **локаль UI ru + en**.
8. **Seed:** faker / вымышленные данные — **OK** (не только пустая БД).
9. Без auth/ролей; **очереди (queues) — осознанно вне scope** (намеренно нет).
10. Стек: отдельные apps **API + UI** по `docs/STACK.md` (в monorepo: `apps/api` + `apps/web`; STACK не использует имя `dashboard` — UI = React/nginx). Docker Compose — да. E2E Playwright — да (QA). ИИ — только процесс + README, не продукт.

## Сущности (продуктово)

- **Сотрудник:** имя (минимум); create / read / **update** / **delete**.
- **Таймер / time entry:** сотрудник, описание, start, stop (null пока running), длительность после стопа; create (через timer + ручной CRUD), read, **update**, **delete**.
- **Период отчёта:** inclusive date range; список + агрегаты; **CSV export**.

## User journeys

### J1 — Сотрудники (полный CRUD)

1. Открыть приложение (без логина); при наличии seed — видны вымышленные сотрудники (faker), иначе пустой список.
2. **Create:** ввести имя → сохранить → появляется в списке и доступен для таймера/отчёта.
3. **Update:** изменить имя существующего сотрудника → список и связанные представления отражают новое имя.
4. **Delete:** удалить сотрудника → исчезает из списка; связанные записи/таймер — поведение согласует eng с целостностью (продуктово: удаление допустимо; не оставлять «битых» ссылок в UI).

### J2 — Учёт времени (start / stop + live + hide)

1. Выбрать сотрудника; ввести непустое описание задачи.
2. **Start** → видно, что таймер идёт: **live elapsed** обновляется в UI.
3. Пользователь может **скрыть** индикатор таймера. При **первом** скрытии — одноразовый confirm: **завершить сессию (Stop)** **или** **скрыть таймер** (сессия продолжает идти).
4. Пока таймер скрыт (collapsed): можно **восстановить** показ elapsed; можно **остановить (Stop)** без разворачивания.
5. **Stop** (в любом состоянии — развёрнут или свёрнут) → запись в истории; running больше нет.

### J3 — Повторный Start при running

1. У сотрудника уже идёт таймер.
2. Попытка Start снова (тот же сотрудник) → **не** создаёт второй running; отказ/сообщение (**AC-6**).
3. После Stop — Start снова разрешён (новое или то же описание).

### J4 — Отчёт за период + CSV

1. Выбрать период (с / по).
2. Видны записи периода и **суммарное время по каждому сотруднику**; желателен общий итог.
3. Пусто → empty state, не сбой.
4. **Export CSV** — скачать данные текущего отчёта (записи / согласованные колонки периода).

### J5 — CRUD записей времени (из отчёта / списка)

1. Найти закрытую (или при необходимости running — по правилам eng) запись.
2. **Edit** поля (описание, интервал — в разумных пределах без ломания «один running на сотрудника»).
3. **Delete** запись → исчезает из списка/отчёта; итоги пересчитываются.

### J6 — Persistence

1. Создать/изменить сотрудников и записи (включая running).
2. Перезапустить приложение / Compose.
3. Данные на месте (SQLite volume).

### J7 — Тема и язык (кратко)

1. Переключить **тёмную / светлую** тему — UI следует выбору (сохранение предпочтения — желательно, не блокер AC если session-only).
2. Переключить язык UI **ru ↔ en** — ключевые лейблы/сообщения на выбранной локали.

## Acceptance criteria

### Сотрудники и данные

- **AC-1.** *(CLARIFIED)* Пользователь может **создать** сотрудника с именем; новый сотрудник отображается в списке без ручной перезагрузки всей системы (UI обновляется после успеха). Update/delete — см. **AC-15**.
- **AC-2.** *(UNCHANGED)* Приложение работает **без** авторизации и **без** ролей: все функции доступны сразу после открытия UI.
- **AC-3.** *(CLARIFIED)* Используются только **вымышленные** данные (нет реальных PII). **Seed через faker (или аналог) допустим и предпочтителен для демо**; пустой старт без seed тоже допустим. Не требуется «только empty DB».

### Таймер

- **AC-4.** *(UNCHANGED)* Пользователь может **запустить** таймер для выбранного сотрудника с **непустым описанием задачи** (Start без описания не принимается).
- **AC-5.** *(CLARIFIED)* Пользователь может **остановить** running-таймер (в т.ч. когда индикатор **свёрнут** — см. **AC-17**); закрывается запись с start/stop и длительностью.
- **AC-6.** *(UNCHANGED смысл; locked)* Пока у **данного сотрудника** есть running-таймер, повторный **Start** для него **отклоняется** (понятное сообщение); второй параллельный running у того же сотрудника не создаётся. Правило: **max один running на employee** (не обязательно «один на всё приложение»).
- **AC-7.** *(UNCHANGED)* После Stop тот же сотрудник может снова Start (новый цикл).

### Отчёт

- **AC-8.** *(UNCHANGED)* Пользователь задаёт период и видит **список записей** (сотрудник, описание, интервал или длительность), относящихся к периоду.
- **AC-9.** *(UNCHANGED)* Для периода отображается **общее время по каждому сотруднику** с записями в периоде.
- **AC-10.** *(UNCHANGED)* **Пустой отчёт:** empty state / «нет данных»; итоги пустые/нулевые; не сбой приложения.

### Persistence и инфраструктура

- **AC-11.** *(UNCHANGED)* Данные (сотрудники и time entries, включая running) **в SQLite** и доступны после перезапуска / Docker Compose (volume).

### Документация, AI-workflow, craft, тесты

- **AC-12.** *(CLARIFIED)* В корневом **README** описаны запуск (в т.ч. Docker Compose), ИИ-инструменты/модели, примеры промптов, что ИИ сделал хорошо vs плохо, какие ошибки исправили вручную. README демонстрирует **AI-workflow разработки**. **ИИ не является функцией продукта / in-app feature** — только процесс + документация.
- **AC-13.** *(CLARIFIED)* Есть автоматизированные проверки основных сценариев, **включая Playwright E2E** ключевых journeys, как минимум: (a) повторный Start при running (**AC-6**); (b) пустой отчёт (**AC-10**); (c) happy-path сотрудник + start/stop (**AC-1**, **AC-4**, **AC-5**); плюс по возможности hide/restore или CRUD smoke — на усмотрение QA в матрице. ### Расширения после grill (NEW)

- **AC-15.** *(NEW)* **Полный CRUD сотрудников:** помимо создания (**AC-1**) пользователь может **изменить** имя и **удалить** сотрудника; изменения отражаются в UI без ручного reload всей системы.
- **AC-16.** *(NEW)* **Полный CRUD time entries:** пользователь может **создавать** (через таймер и/или явное создание), **просматривать**, **редактировать** и **удалять** записи времени; отчёт/список и итоги обновляются после изменений. Редактирование не должно обходить **AC-6** (не допускать два running у одного сотрудника).
- **AC-17.** *(NEW)* **Live elapsed** для running-таймера отображается в UI. Пользователь может **скрыть** таймер; при **первом** скрытии показывается **одноразовый** confirm: **завершить сессию** или **скрыть**. После скрытия: **восстановить** показ; **Stop доступен в свёрнутом состоянии**. Повторные hide после первого выбора «скрыть» — без повторного confirm.
- **AC-18.** *(NEW)* **CSV export** текущего отчёта (данные за выбранный период) — пользователь может скачать файл; содержимое согласовано со списком/полями отчёта (минимум: сотрудник, описание, интервал/длительность).
- **AC-19.** *(NEW)* **Переключение темы** light / dark доступно в UI; выбранная тема применяется к основным поверхностям приложения.
- **AC-20.** *(NEW)* **Локализация UI:** доступны языки **ru** и **en**; пользователь переключает локаль; ключевые лейблы, кнопки и сообщения ошибок/empty states отображаются на выбранном языке.

## Вне scope (явно)

- Auth, RBAC, SSO
- Проекты, клиенты, теги, billing, calendar/timesheet grid
- Мультитенантность, мобильные клиенты, офлайн-sync
- Ручной ввод длительности **вместо** таймера как единственный режим — вне минимального scope (CRUD записей с правкой интервала — **в scope** через **AC-16**)
- **Очереди (message queues / job queues) — осознанно нет** (intentionally out of scope; не блокер планирования)
- In-app AI-чат / AI-фичи продукта — нет (только AI в процессе разработки + README, **AC-12**)
